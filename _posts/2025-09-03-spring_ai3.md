# Tool Calling

Tool Calling은 LLM이 외부 시스템 기능을 호출해 능력을 확장하는 기능이다. Function Calling이라고도 불린다. 기본적으로 LLM은 들어온 텍스트를 읽고 텍스트를 내보내므로 DB 조회, 실시간 날씨나 최신 정보 검색, 파일 읽기 등의 업무는 LLM 혼자서 할 수 없으니 외부 도구를 사용하게 만드는 것이다. 

## 전체 흐름

Tool Calling의 개략적인 흐름은 다음과 같다.
**LLM은 직접 Java 메서드를 호출하지 않는다.**

1. LLM에게 사용 가능한 Tool 목록 전달
2. LLM이 어떤 Tool을 쓸지 판단
3. LLM이 Tool 이름 + 파라미터 반환
4. Spring AI가 Tool 실행
5. 실행 결과를 다시 LLM에 전달
6. LLM이 결과를 바탕으로 최종 답변 호출

## Tool Definition

LLM에게 어떤 Tool이 있는지 알려주기 위해 Tool 마다 정의를 알려준다. 보통 Tool 정의에는 Tool Name, Description, Input Schema 등이 포함된다.

### 예시

우선 사용할 Tool에 대한 Definition 클래스를 정의한다.

```java
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;

@Component
@Slf4j
public class DateTiemTools {
  @Tool(description = "도시 이름으로 현재 날씨를 조회합니다.")       // 이 메서드가 무슨 기능인지 LLM에게 설명
  public String getCurrentWeather(
      @ToolParam(description = "도시 이름", required = true)  // 파라미터가 무슨 뜻인지 LLM에게 설명, required 기본 값 true
      String city
  ) {
      ...
  }
}
```

실제로 tool을 사용하기 위해서는 chatClient에 붙여주어야 한다.
아래와 같은 방법으로 `.tools()`를 통해 등록한 tool 정보를 포함한 프롬프트 메세지를 Spring AI가 LLM에게 전달한다.

```java
@Autowired
private final DateTimeTools dateTimeTools;

return chatClient.prompt()
    .user(request)
    .tools(dateTimeTools)   // 이번 LLM 요청에서 사용할 수 있는 tool 등록
    .call()
    .content();
```

이후 LLM에서 도구를 사용하겠다고 결정하면 Assistant Message에 사용 Tool 정보를 Spring AI로 응답한다. Spring AI 내에서 Tool 메소드를 호출하고, 돌아온 @Tool 메소드 응답은 ToolResponse 메세지로 전환해 LLM에게 전달한다. LLM은 ToolResponse 메세지 정보 기반으로 응답을 생성하고 그 응답을 Spring AI에게 전달한다.

# MCP

MCP는 자연어로 생각하는 AI와 API/DB/업무 시스템 같이 구조화된 외부 시스템을 연결하기 위한 표준 프로토콜이다.
단순히 답변만 하는 LLM을 외부 시스템과 연결해서 실제로 행동하는 agetn로 확장하기 위한 표준이라고 보면 된다.

쉽게 생각하면 앞선 @Tool과 비슷하다. 일반 Tool Calling은 `LLM -> Spring AI -> 같은 애플리케이션의 JAVA 메서드 실행`의 흐름을 가진다.
MCP는 `LLM -> Spring AI / MCP Client -> MCP Server -> 원격 Tool 실행`이다.
둘의 차이는 **Tool이 어디 있느냐**.

```text
@Tool       → 로컬 Java 메서드
@McpTool    → MCP Server가 외부에 제공하는 Tool
```

실제 코드에서도 tool controller 파일에서 `@Tool`, `@ToolParam`만 바꾸면 된다.

## 구조

```text
사용자
  ↓
Host (AI Application)
  ↓
MCP Client
  ↓
MCP Server
  ↓
DB / API / 파일 / 외부 시스템
```

- Host: 사용자 요청을 받는 LLM을 포함한 AI 애플리케이션
- MCP Client: MCP 통신 담당. `tools/list`로 도구 목록을 받고, `tools/call`로 실제 tool 실행을 요청한다
- MCP Server: 외부 기능을 Tool/Resource 형태로 제공

## 전체 흐름

이제 MCP의 큰 흐름을 알아보자

1. MCP Client → Server

   `tools/list`

2. Server → Client

   사용 가능한 Tool Definition 반환

3. 사용자 질문 + Tool Definition

   → LLM

4. LLM

   "이 Tool 써줘"
   tool_calls 반환

5. MCP Client → MCP Server

   `tools/call`

6. MCP Server

   실제 Tool 실행

7. 결과 → MCP Client

8. ToolResponseMessage → LLM

9. LLM 최종 답변 생성

## ToolCallbackProvider

Spring AI가 쓸 수 있는 Tool들을 한꺼번에 제공해주는 공급자다.
MCP Client 서버가 `tools/list` 요청을 보내서 tool 목록을 받아온다.
그 MCP Tool을 Spring AI가 이해하는 `ToolCallback` 형태로 바꾸고, 그 `ToolCallback`들을 묶어서 제공하는 게 `ToolCallbackProvider`다. 
Tool Calling에서 `.tools(ToolName)`했던 것과 비슷하게 `tools(mcpToolCallbackProvider)`로 쓸 수 있다. 

- **ToolCallback** : Tool 하나를 실행할 수 있게 감싼 객체
- **ToolCallbackProvider** : 그런 `ToolCallback` 여러 개를 제공하는 객체

## MCP의 통신 방식

MCP 통신은 3계층 아키텍처를 따른다.

1. Client/Server Layer

   - 최상단. Java/Python 객체 중심으로 MCP 통신 처리 구간
   - 어떤 Tool이 있는지 LLM에게 알려준다
   - Java 객체, Tool Definition, ToolCallback 등

2. MCP Session

   - 중간 단계. 클라이언트-서버 간 사전 정보 교환, 표준 Json Schema 변경 전달
   - 우리 어떤 MCP 버전으로 대화할까
   - 초기화, Capability 협상, JSON-RPC 메세지 관리

3. Transport Layer

   - 최하단. tool 호출 정보를 전달하기 위한 전달 계층 (STDIO, HTTPS 통신)
   - 실제 데이터를 STDIO로 보낼지 HTTP로 보낼지
   - STDIO, Streamable HTTP, Stateless Streamable HTTP

### 호출 흐름

1. Client가 지원 MCP Protocol Version, Client 정보, Client Capability, 즉 사전에 서로 알아야 할 정보를 전달한다
2. 서버가 사용할 MCP Protocol Version, Server Capability를 반환한다
3. 초기화가 끝나고, 정상 메세지 교환 가능 알림이 전달된다


## MCP Transport Layer

이번 장에서는 가장 최하단의 Transport Layer를 자세히 알아볼 것이다.
MCP Client와 MCP Server는 JSON-RPC 메세지로 통신을 수행한다. 
  
- JSON-RPC : JSON으로 원격 함수를 호출하고 결과를 JSON으로 받는 프로토콜

### STDIO

표준 입출력 STDIO(standard input / standard output). 애플리케이션 시작 시 같은 PC에서 MCP Client와 Server를 실행하는 경우에 사용하는 통신 방식이다.
LLM으로부터 도구 호출 요청이 들어오면 MCP Client는 STDIO를 이용해 MCP Server와 통신한다.

- **장점**
  - 가장 단순. 에디터/IDE/로컬 프로세스 통합에 효과적
  - HTTP 서버 필요 없음
  - 네트워크 포트 필요 없음
  - 서버는 단순히 STD 입력 읽고 STD 출력으로 결과 쓰기만 함
  - **데이터는 반드시 JSON-RPC 2.0 메세지**

### Stateful Streamable HTTP

- HTTP: 애플리케이션과 MCP Server 간 **원격**에서 개별적으로 실행하는 경우 통신하는 방식

서버가 Client와의 세션 상태를 기억하는 MCP HTTP 통신이다.
기본 요청은 `POST /mcp`이며 그 응답을 SSE Stream으로 유지해 서버 로컬에 세선 상태를 보관할 수 있다.
처음 초기화하면 서버가 `Mcp-Session-Id`를 발급해 이후 요청에 전달하여 동일한 세션인지 식별이 가능하다.

- **장점**
  - 장기 실행 작업 가능
  - progress 전달
  - 세션 기반 상호작용 가능
- **단점**
  - 서버가 세션을 기억해야 함
  - 여러 서버/Pod로 늘리기 어려움
- **용도**
  - 대화/구독/진행상태

### Stateless Streamable HTTP

각 요청이 완전히 독립적인 MCP HTTP이다. 서버는 이전 대화에서 무슨 요청을 했는지 기억하지 않는다.
기본 요청은 `POST /mcp`로 동일하며 개별적으로 요청/응답 처리한다.
세션을 따로 식별하지 않으며, 따라서 보통 `Mcp-Session-Id`도 없다.

- **장점**
  - 수평 확장이 쉽다
  - Cloud Native / Kubernetes 에 유리하다
  - 세션 저장할 필요가 없다
- **단점**
  - 서버가 이전 연결 상태를 이용하기 어렵다
  - 장기 상태 기반 작업에서는 상대적으로 불리하다
- **용도**
  - 조회/계산/API형 Tool

## 전체 구조 

```text
                    사용자
                      ↓
                 Spring App
                 (MCP Host)
                      ↓
                    LLM
                      │
             "Tool 필요하겠다"
                      ↓
             MCP ToolCallbackProvider
                      ↓
                  MCP Client
                      │
              JSON-RPC 2.0
                      │
        ┌─────────────┴─────────────┐
        │                           │
      STDIO                  Streamable HTTP
        │                           │
        └─────────────┬─────────────┘
                      ↓
                  MCP Server
                      ↓
             @McpTool 메서드
                      ↓
               DB / API / Files
```
